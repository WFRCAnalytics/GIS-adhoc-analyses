Purpose

For six WCV centers – Daybreak, Saratoga Springs Downtown, The Point, Ogden Downtown, Clearfield, and Farmington Station Park – this answers three questions per center:

  1. Current year (2025) homes and jobs – where things stand today.
  2. 2055 forecast homes and jobs – REMM’s own simulated outcome by 2055.
  3. Full REMM capacity homes and jobs – see ## Full REMM capacity below; the method differs by center, since The Point’s is already fully built out by 2055 per REMM (nothing developable left), while every other center still has land redeveloping past 2025 whose additional capacity has to be estimated from density assumptions.

Metrics 1 and 2 use one shared calculation for every center. See ## Summary for the combined results and CSV exports (chart pending).

Spatial joins, filtering, and aggregation below run in geopandas/pandas. The base-year parcels come from remm_base_year_data.gdb, which is cached as GeoParquet on first run (see below) so later runs just read that instead of re-parsing the FileGDB.

Centers of interest

Single ordered list to extend if more centers are added later. center_boundaries is fetched in full from the REST service (no server-side where), so adding a center here doesn’t require touching sources.yml or re-fetching – just delete _data/processed/centers.parquet to force it to rebuild with the updated list.

Not every raw center_boundaries row we need is a CenterType = 'Urban Center' polygon the way the original three were – checked directly against the source’s attribute table:

  • Ogden Downtown is CenterType = 'Metropolitan Center'.
  • Clearfield isn’t a single polygon at all – it’s the combination of three separate raw CenterName rows: Downtown Clearfield (Urban Center), Clearfield Station (Urban Center), and Downtown Gateway (South) (City Center).
  • Farmington Station Park is the raw row named just Station Park (City = 'Farmington', Urban Center) – center_boundaries doesn’t prefix it with the city name the way the analysis name does.

So the where-filter below can no longer blanket-restrict to CenterType = 'Urban Center' (that would silently drop Ogden Downtown and Clearfield’s City Center piece). It instead fetches by exact raw CenterName, excluding only CenterType = 'Employment District' – the one type that would otherwise pull in The Point’s redundant second polygon (its only raw-name collision; every other raw name below is unique in the source). A RAW_TO_ANALYSIS mapping then folds Clearfield’s three raw rows down to one analysis center – applied once, right after the fetch, so every downstream groupby("CenterName") naturally aggregates across all three of Clearfield’s polygons without further changes.

REMM parcels: load and cache as parquet

Show the code 
from pathlib import Path

import geopandas as gpd
import pandas as pd

paths = {
    "raw": Path("_data/raw"),
    "processed": Path("_data/processed"),
}
paths["processed"].mkdir(parents=True, exist_ok=True)

paths.update({
    "gdb": paths["raw"] / "remm" / "remm_base_year_data.gdb",
    "buildings_2055_pkl": paths["raw"] / "remm" / "run1842year2055allbuildings.pkl",
    "progression_2055_pkl": paths["raw"] / "remm" / "run_1842_year_2055_parcel_progression_metrics.pkl",
    "parcels_geoparquet": paths["processed"] / "parcels_2023.parquet",
    "centers_geoparquet": paths["processed"] / "centers.parquet",
    "buildings_2055_parquet": paths["processed"] / "buildings_2055.parquet",
    "progression_2055_parquet": paths["processed"] / "progression_2055.parquet",
})

# one-time read of the two vector sources, cached as GeoParquet so later runs
# don't re-parse the FileGDB or re-fetch the REST layer. Each cache is a full
# replica of every source column -- selecting only the columns actually
# needed for a given step happens later, at read time (via `columns=`), not
# by trimming what gets cached here.
if not paths["parcels_geoparquet"].exists():
    parcels_gdf = gpd.read_file(paths["gdb"], layer="parcels")
    # Split_Factor/MAG_parcel_id mix strings with a couple of real NaNs, which
    # pyarrow can't write as a single column type -- nullable string dtype
    # keeps those as actual nulls (not the literal string "nan").
    parcels_gdf["Split_Factor"] = parcels_gdf["Split_Factor"].astype("string")
    parcels_gdf["MAG_parcel_id"] = parcels_gdf["MAG_parcel_id"].astype("string")
    parcels_gdf.to_parquet(paths["parcels_geoparquet"])

if not paths["centers_geoparquet"].exists():
    centers_gdf = gpd.read_file(
        L["center_boundaries"],
        where=f"CenterName IN ({', '.join(map(repr, RAW_CENTER_NAMES))}) AND CenterType <> 'Employment District'",
    )
    # fold Clearfield's three raw polygons (and every other 1:1 raw name)
    # down to their analysis center name here, once, so every downstream
    # groupby("CenterName") aggregates across all of a center's raw rows
    # without needing to know Clearfield is special.
    centers_gdf["CenterName"] = centers_gdf["CenterName"].map(RAW_TO_ANALYSIS)
    centers_gdf.to_parquet(paths["centers_geoparquet"])

if not paths["buildings_2055_parquet"].exists():
    buildings_full = pd.read_pickle(paths["buildings_2055_pkl"]).reset_index()
    # 'note' mixes real strings with an int 0 sentinel (no dedicated null),
    # which pyarrow can't write as a single column type. 0 means "no note", so
    # it's replaced with an actual null rather than becoming the string "0".
    buildings_full["note"] = buildings_full["note"].replace(0, pd.NA).astype("string")
    buildings_full.to_parquet(paths["buildings_2055_parquet"])

if not paths["progression_2055_parquet"].exists():
    # no mixed-type columns here, so a plain conversion is enough
    pd.read_pickle(paths["progression_2055_pkl"]).to_parquet(paths["progression_2055_parquet"])

# only the columns needed for the spatial join below (geometry + acreage/name) --
# other columns (max_far, max_dua, DwellingPerAcre, ...) get pulled later, from
# the same cached files, only where they're actually used.
parcels = gpd.read_parquet(paths["parcels_geoparquet"], columns=["parcel_id", "parcel_acres", "geometry"])
centers = gpd.read_parquet(
    paths["centers_geoparquet"], columns=["CenterName", "CenterType", "geometry"]
).to_crs(parcels.crs)  # centers ships in EPSG:4326 (WGS84) from the REST layer; parcels are in EPSG:26912 (UTM 12N)

Parcels within each center

Centroid-in-polygon join (not a straight intersection) so a parcel straddling a center boundary is assigned to exactly one center, not double-counted.

Show the code 
# swap each parcel's polygon for its centroid point -- a polygon can legitimately
# intersect two centers along a shared edge, but its centroid falls in exactly one.
parcel_centroids = parcels.set_geometry(parcels.geometry.centroid)

# predicate="within": keep a parcel only if its centroid point falls inside a
# center polygon. how="inner" drops parcels whose centroid falls in no center
# at all (most of the region -- centers are a tiny fraction of all parcels).
parcels_in_centers = gpd.sjoin(
    parcel_centroids, centers[["CenterName", "geometry"]], predicate="within", how="inner"
)[["parcel_id", "parcel_acres", "CenterName"]]

parcels_per_center = parcels_in_centers.groupby("CenterName").agg(
    n_parcels=("parcel_id", "count"), total_acres=("parcel_acres", "sum")
)

Metric 1: current year (2025) homes and jobs

No dedicated 2025 REMM run exists (only “2023” and “2055” pickles), so this derives 2025 by filtering the 2055 run’s buildings table (run1842year2055allbuildings.pkl, one row per building) to year_built <= 2025 and summing residential_units/job_spaces per center. One shared calculation for every center.

Data quality note: filtering to year_built <= 2023 instead reproduces the dedicated run1842year2023allbuildings.pkl exactly for Daybreak (905 units/2,389 jobs) and Saratoga Springs Downtown (0/0), but not for The Point (2023 pickle: 0 units/2,474 jobs vs. 2055-run-filtered: 0/978) – the two REMM runs disagree on The Point’s historical baseline. Proceeding with the uniform year_built <= 2025 method regardless: The Point was a state prison site until recently, so a real drop from ~2,474 jobs (2023, pre-closure) to ~978 (2025, post-closure/pre-redevelopment) is a plausible read, not necessarily a data error – consistent with satellite imagery showing The Point still mostly undeveloped today. This same 2025-derivation method applies uniformly to Ogden Downtown, Clearfield, and Farmington Station Park too – no dedicated 2023/2025 pickle exists for any center beyond the original three, so there’s no equivalent cross-check available for them.

buildings_2055 = pd.read_parquet(

    buildings_2055[buildings_2055["year_built"] <= 2025]
    .merge(our_parcels[["parcel_id", "CenterName"]], on="parcel_id")

Full REMM capacity (metric 3)

Method differs by center:

  • Every center except The Point: developable acreage (parcels with a building year_built > 2025) x forecast res/nonres mix ratio x median density assumptions = additional housing units/jobs on top of today’s baseline (metric 1) – not an absolute total by itself. Combined with metric 1 in ## Summary to get a comparable absolute figure.
  • The Point: no separate development schedule document was ever provided, and The Point is already REMM-modeled, so “the development schedule” here means REMM’s own full-buildout simulation directly (no density-assumption modeling needed) – REMM shows 0 parcels still developable there as of 2055, so this figure already is an absolute total, identical to its metric 2 (2055 forecast).

Developable land

Follows the original pseudocode directly: filter the 2055 buildings table to parcels within our centers of interest, keep buildings with year_built > 2025, take the unique parcel ids from that, then sum parcel_acres for those parcels. Computed for every center here too (The Point’s result is an exploratory cross-check only – see above).

An earlier version of this shortcut off the parcel-level parcel_progression_metrics table instead, since it already carries a single year_built per parcel. That’s only valid if every building on a parcel always shares the same year/type – checked directly: 162 parcels regionwide have more than one building, 2 of them are in our centers of interest, and in both cases the buildings on that parcel happened to share the same year_built. That was a coincidence of this dataset, not something the data guarantees in general, so this filters at the building level as originally specified rather than relying on it holding elsewhere.

Show the code 
# inner join: only buildings whose parcel_id is one of our centers' parcels survive.

Forecast development mix and buildout capacity

(1) Forecast residential : commercial/employment development ratio

Sum residential_units and job_spaces from parcel_progression_metrics for the post-2025 developable parcels identified above (2055 run). Full buildout of each center is assumed to follow this same mix, so each center’s total developable acreage is allocated between residential and commercial/employment by this ratio.

Show the code 
dev_mix = (
    our_parcels[our_parcels["parcel_id"].isin(post_2025_parcel_ids)][["parcel_id", "CenterName"]]
    .merge(progression_2055, on="parcel_id")
    .groupby("CenterName")[["residential_units", "job_spaces"]]
    .sum()
)
dev_mix["unit_job_ratio"] = dev_mix["residential_units"] / dev_mix["job_spaces"]

# res_share/nonres_share are the same ratio re-expressed as shares of a whole
# (res_share = unit_job_ratio / (unit_job_ratio + 1)) -- this is what actually
# gets multiplied against acreage below.
dev_mix["res_share"] = dev_mix["residential_units"] / (dev_mix["residential_units"] + dev_mix["job_spaces"])
dev_mix["nonres_share"] = 1 - dev_mix["res_share"]

(2) Apply density assumptions to each acreage share

Median dwelling-units-per-acre and FAR. max_far/max_dua live on the parcels table (per-parcel zoning capacity, not a text range), so this takes the statistical median across all parcels in each center – not just the post-2025 developable ones, since the assumption is about the center’s overall zoned capacity, not only what’s forecast to redevelop. Josh noted REMM’s own FAR/DUA-driven numbers assume a parcel develops wall-to-wall (no roads, parking, or common space carved out), so if that assumption changes later, override the values directly here (e.g. capacities.loc["Daybreak", "median_far"] = 2.0) and rerun from this cell down.

Known limitation: for Daybreak specifically, several of its post-2025 developable parcels are large master-planned “super-parcels” whose actual REMM-simulated density (up to ~280 units/acre on parcels with a recorded max_dua of just 30) far exceeds their generic zoning entitlement – Daybreak’s real approved density (high-rise towers via a specific development agreement) isn’t fully captured by the max_far/max_dua fields. This makes the density-assumption-based capacity estimate understate what REMM’s own simulation already achieves – visible in ## Summary below, where both Daybreak’s and Saratoga Springs Downtown’s metric 3 homes figures come in below their metric 2 (2055 forecast) despite being meant as a ceiling on top of it. Left as-is for now (including in the ## Plots chart below, where it makes the nested bar encoding render oddly for these two) pending a fix to the density assumption itself.

The Point: full buildout

Unlike Daybreak/Saratoga Springs Downtown, this doesn’t need acreage allocation or density assumptions: REMM’s simulated buildings already give unit/job counts directly, so this is just a sum, plus a check that nothing’s left undeveloped (rather than an estimate of it). This is the actual full-capacity figure for The Point – the developable-land/density- assumption method above was computed for The Point too, but only as an exploratory cross-check (see capacity.loc["The Point"], which is NaN for housing_units since none of its parcels have a max_dua entitlement yet).

Show the code 
# residential_units/job_spaces here are absolute totals as of the 2055 run
# (not "_added" deltas) -- i.e. REMM's full-buildout state, not "new since 2025".
# developable/year_built/max_far/max_dua are pulled too, for the check below.
point_progression = pd.read_parquet(
    paths["progression_2055_parquet"],
    columns=["parcel_id", "residential_units", "job_spaces", "developable", "year_built", "max_far", "max_dua"],
)

point_parcels = parcels_in_centers[parcels_in_centers["CenterName"] == "The Point"]
point_buildout = point_parcels[["parcel_id", "parcel_acres"]].merge(point_progression, on="parcel_id")

# developable == 1 would mean "still vacant and buildable as of 2055" -- expect
# none, confirming there's no residual land to separately estimate.
still_developable = point_buildout[point_buildout["developable"] == 1]
print(f"parcels still flagged developable: {len(still_developable)}")

# parcels with no building recorded (year_built == 0) are only a gap if they
# also have real zoning capacity -- if max_far/max_dua are both 0 too, they're

Sensitivity: DUA/FAR scenarios

The density assumptions above (median_dua/median_far, from each center’s own zoning entitlements) turn out to badly understate what REMM’s own simulation actually builds on this land. Walking Metric 3’s formula backward from REMM’s 2055 forecast for the post-2025 developable parcels themselves (same res_acres/nonres_acres, just solving for density instead of units) gives implied densities around 155 DUA / 1.3 FAR for Daybreak and 37 DUA / 0.3 FAR for Saratoga Springs Downtown, vs. zoning medians of 30 DUA/7.0 FAR and 10 DUA/0.5 FAR respectively – a real gap, not noise. Rather than committing to one “fixed” density assumption, this applies the same res_acres/nonres_acres x density formula across a fixed grid of alternative densities, so the capacity estimate can be shown as a range instead of a single number.

Applied to every center, including The Point – even though its own “current” capacity estimate uses REMM’s full-buildout simulation directly rather than a density assumption (median_dua isn’t even defined for it; none of its parcels carry a max_dua entitlement yet), the constant dua/far scenarios below still apply the same acreage-based formula to it using its own res_acres/nonres_acres/sqft_per_job (computed earlier only as an exploratory cross-check), so it can be compared on the same scenario grid as every other center.

  • Residential: dua = each center’s own zoning median (current method, undefined for The Point) or a fixed 50/100/150 du/acre.
  • Nonresidential: far = each center’s own zoning median (current method) or a fixed 0.75/4.0 FAR.

For every center except The Point, the “current” row reproduces capacity.loc[center]/housing_capacity/jobs_capacity from above exactly (same formula, same inputs) – included here as a consistency check as much as a scenario. For The Point, “current” instead pulls point_capacity directly, so capacity_added is left blank there: REMM’s full-buildout simulation is a direct absolute total, not decomposed into a 2025-baseline- plus-added-development estimate the way the formula-based scenarios are.

Plots

Both employment and housing render below, each extended with the sensitivity scenarios from ## Sensitivity: DUA/FAR scenarios as an overlay on top of the original chart – not a separate chart – so the density-assumption uncertainty shows up right on the same bars analysts already read.

Horizontal bars, editorial styling inspired by Tanya Shapiro’s ggplot work: left-aligned bold title/subtitle, direct value labels instead of relying on axis ticks, minimal chart junk (no spines, no gridlines), and the WFRC brand’s own typeface (Poppins) instead of matplotlib’s default font – Inter (the brand’s heading font) turned out to only be installed as a variable font at weight 400, so Poppins SemiBold (a proper static weight) carries the title/value labels instead, keeping one cohesive typeface throughout rather than mixing families. Centers are fixed to index.qmd’s own canonical CENTERS_OF_INTEREST order in both charts – rather than each chart sorting by its own capacity column – so a center sits in the same row in both.

Each bar is a Meter-style nested encoding (see the dataviz skill: fill = value, track = a lighter step of the same hue), extended from 2 tiers to 3, with all three values labeled (not just capacity) – though the capacity tier is currently toggled off from the render (SHOW_CAPACITY_TIER = False below hides the track bar, its bold value label, its subtitle mention, and its legend entry together, without deleting the computation – flip it back to True to restore all four at once):

  • Track (full bar length): full REMM capacity – lightest tint of the center’s hue.
  • Hatch overlay (0 to the 2055 figure): tone-on-tone diagonal texture – how much of that capacity REMM’s own simulation reaches by 2055. Skipped for The Point, where 2055 forecast == capacity exactly (nothing left developable), to avoid labeling the same value twice. For every other center’s housing chart, if housing_2055 ends up above housing_capacity (the density-assumption method’s known limitation, first observed on Daybreak/SSD and discussed above), that’s an honest reflection of the method understating real achievable density, not a rendering bug – the hatch overlay extends past the light-shade track there instead of nesting inside it.

Colors are 6 categorical hues – one per center – drawn from the WFRC brand’s Core Palette (blue, orange, green, purple, gold, red), chosen over the “Wasatch Choice Center” colors since centers span multiple CenterTypes and would collide under that scheme. The original three centers keep their exact original hues (blue #036fa8, orange #ea7b00, green #007426); purple and gold are nudged slightly off their literal brand hex (#553c8f -> #5f4494, #eab500 -> #c9a000) to clear the dataviz skill’s lightness-band check, and the 6-color set is both reordered and re-nudged until validate_palette.js passes clean in this exact row order – worst adjacent pair (green/orange) clears CVD at 11.7, with only the usual contrast WARN on orange and gold (both satisfied by the always-visible bold value labels, per the skill’s relief rule).

Sensitivity overlay, drawn directly on top of each existing bar:

  • A small vertical tick at each alternate scenario’s capacity_total, plus a thin neutral bracket connecting the tested range into one span. Ticks (and their value labels) get their own fixed color per scenario – not per center, since centers are already distinguished by row + the tier hues – from a light-to-dark teal ordinal ramp (50 < 100 < 150 du/ac; 0.75 < 4.0 FAR is an ordered category, not an arbitrary categorical palette), with a second legend row mapping each color to its scenario. Teal specifically because it’s the one hue-family gap left once all 6 centers claim blue/orange/green/purple/gold/red – validated separately with --ordinal (monotone lightness, adjacent steps, light-end contrast), since a sequential ramp fails the categorical six by design.
  • The Point’s dua_100/dua_150/far_4.0 scenarios are genuine order-of-magnitude outliers (its land area dwarfs every other center’s, so a flat per-acre assumption blows past everything else) – stretching the shared axis to fit them would compress every other bar into a sliver, so the axis instead caps at 1.3x the existing capacity-tier max, and anything past that renders as an off-scale > marker with an asterisked value instead of distorting the whole plot.
  • Every label – the pre-existing 2025/2055/capacity labels and the new scenario labels – draws at a higher zorder than the bracket/tick lines, and the bold capacity label additionally gets a surface-colored path_effects halo: the tested range regularly extends past capacity, so without this the bracket line would render through that number instead of behind it.
  • Figure height and the title/subtitle/legend margins scale with the number of centers (an absolute-inches header/footer budget, not a fixed figure-fraction) – a fixed-fraction header sized for 3 rows would either crush 6 rows’ worth of bars into no vertical room, or leave a disproportionate blank margin above 3.

def lighten(hex_color, amount):
    """Blend hex_color toward white by `amount` (0=no change, 1=white)."""
    hex_color = hex_color.lstrip("#")
    r, g, b = (int(hex_color[i:i + 2], 16) for i in (0, 2, 4))
    r, g, b = (int(c + (255 - c) * amount) for c in (r, g, b))
    return f"#{r:02x}{g:02x}{b:02x}"


def declutter_depths(xs, min_gap):
    """Given x-positions (any order), return a same-length list of stack
    depths (0, 1, 2, ...) so any two positions closer than min_gap land at
    different depths -- greedy, walked in x order. Used to keep same-row
    labels from overlapping when their underlying values happen to sit close
    together (e.g. Ogden Downtown's 2025/2055/FAR-scenario jobs figures all
    landing within ~1-2% of each other) -- a collision the original 3-center
    data never triggered, but real numbers for the added centers did."""
    order_idx = sorted(range(len(xs)), key=lambda i: xs[i])
    depths = [0] * len(xs)
    last_x, depth = None, 0
    for i in order_idx:
        x = xs[i]
        depth = depth + 1 if last_x is not None and (x - last_x) < min_gap else 0
        depths[i] = depth
        last_x = x
    return depths

    order = CENTER_ORDER

    # modest extra row spacing (vs. a plain unit-spaced chart) so the
    # per-scenario tick labels below each bar have room to breathe
    row_gap = ROW_GAP
    ys = [i * row_gap for i in range(len(order))]
    axes_data_range = (len(order) - 1) * row_gap + 1.7
    fig_height = HEADER_HEIGHT_IN + IN_PER_DATA_UNIT * axes_data_range + FOOTER_HEIGHT_IN

    fig, ax = plt.subplots(figsize=(9.5, fig_height), dpi=140)
    fig.patch.set_facecolor(SURFACE)
    ax.set_facecolor(SURFACE)

    bar_height = 0.5
    # axis scale anchors on the largest value actually drawn: capacity
    # itself when its tier is shown, but the 2055 forecast (the tallest
    # remaining visible tier) once capacity is hidden -- otherwise the axis
    # keeps stretching to fit an invisible number, wasting most of the
    # chart's width on empty space (most visible for employment, where
    # capacity's max of 81,979 dwarfs the 2055 max of 18,110; housing's two
    # maxes happen to sit close together -- 7,908 vs. 7,834 -- so it barely
    # moves there). The off-scale/clip-and-asterisk handling below doesn't
    # change at all -- it just now triggers for more scenario values, which
    # it was already built to handle.
    base_max = summary[cfg["summary_cap"]].max() if SHOW_CAPACITY_TIER else summary[cfg["summary_2055"]].max()
    clip_limit = base_max * 1.3
    in_range_alts = [alt[(c, s)] for c in order for s in cfg["alt_scenarios"] if alt[(c, s)] <= clip_limit]
    xmax = max([base_max, *in_range_alts])
    # off-scale markers/labels anchor a fixed distance PAST xmax (not a
    # fraction below it) -- with 6 centers, one center's own borderline
    # in-range scenario can land close enough to xmax itself (e.g.
    # Farmington's dua_50 at 9,994 against an xmax of 9,994) that an
    # edge_x defined as a fraction *below* xmax would collide with that
    # legitimate in-range tick's label. Anchoring past xmax instead keeps
    # off-scale content clear of every in-range tick, always.
    EDGE_X = xmax * 1.05
    any_clipped = False

    for i, center in enumerate(order):
        y = ys[i]
        hue = CENTER_COLORS[center]
        cap = summary.loc[center, cfg["summary_cap"]]
        forecast = summary.loc[center, cfg["summary_2055"]]
        current = summary.loc[center, cfg["summary_2025"]]

        if SHOW_CAPACITY_TIER:
            ax.barh(y, cap, height=bar_height, color=lighten(hue, 0.8), zorder=1)
        ax.barh(y, forecast, height=bar_height, facecolor="none", hatch="///", edgecolor=lighten(hue, 0.25), linewidth=0, zorder=2)
        ax.barh(y, current, height=bar_height, color=hue, zorder=3)

        top_y = y + bar_height / 2
        LABEL_Z = 6  # every label out-ranks the bracket (4) and tick (5) lines
        # skip forecast's own label only when it would duplicate a VISIBLE
        # bold capacity label (The Point: forecast == capacity exactly) --
        # with the capacity tier hidden, that number isn't shown anywhere
        # else, so forecast's label always earns its place.
        show_forecast = not SHOW_CAPACITY_TIER or not np.isclose(forecast, cap, rtol=0.001)
        # bump the forecast label above the current label (rather than
        # side by side at the same height) when the two values sit close
        # enough that their text would otherwise overlap horizontally.
        forecast_bump = 0.16 if show_forecast and abs(forecast - current) < xmax * 0.08 else 0.0
        if current > 0:
            ax.text(current, top_y + 0.07, f"{current:,.0f}", ha="center", va="bottom", fontsize=8.5, color=TEXT_MUTED, zorder=LABEL_Z)
        else:
            ax.text(current, top_y + 0.07, "0", ha="left", va="bottom", fontsize=8.5, color=TEXT_MUTED, zorder=LABEL_Z)
        if show_forecast:
            ax.text(forecast, top_y + 0.07 + forecast_bump, f"{forecast:,.0f}", ha="center", va="bottom", fontsize=8.5, color=TEXT_MUTED, zorder=LABEL_Z)
        if SHOW_CAPACITY_TIER:
            ax.text(cap + xmax * 0.015, y, f"{cap:,.0f}", ha="left", va="center", fontsize=11, color=TEXT_PRIMARY,
                    fontfamily="Poppins SemiBold", zorder=LABEL_Z,
                    path_effects=[pe.withStroke(linewidth=3, foreground=SURFACE)])

        # --- sensitivity overlay ---
        alt_pairs = list(zip(cfg["alt_ticks"], (alt[(center, s)] for s in cfg["alt_scenarios"])))
        in_range = [(lab, v) for lab, v in alt_pairs if v <= clip_limit]
        clipped = [(lab, v) for lab, v in alt_pairs if v > clip_limit]
        tick_top, tick_bot = y + bar_height / 2 + 0.09, y - bar_height / 2 - 0.09

        if in_range:
            vals = [v for _, v in in_range]
            ax.plot([min(vals), max(vals)], [y, y], color=BRACKET_INK, linewidth=1.4, zorder=4, solid_capstyle="round")
            # ticks draw at their true value regardless; only the text label
            # stacks deeper when two scenario values sit close together.
            depths = declutter_depths(vals, min_gap=xmax * 0.08)
            for (lab, v), depth in zip(in_range, depths):
                sc_color = cfg["scenario_colors"][lab]
                ax.plot([v, v], [tick_bot, tick_top], color=sc_color, linewidth=2, zorder=5)
                ax.text(v, tick_bot - 0.03 - depth * 0.14, f"{v:,.0f}", ha="center", va="top", fontsize=7.6,
                        color=sc_color, fontfamily="Poppins SemiBold", zorder=LABEL_Z)
        if clipped:
            any_clipped = True
            ax.plot([EDGE_X], [y], marker=">", markersize=6, color=BRACKET_INK, zorder=5)
            # dark-green end-cap tick just past the arrow, in the same
            # vertical style as the in-range scenario ticks -- reads as
            # "the range keeps going here" rather than a hard stop.
            ax.plot([EDGE_X + xmax * 0.006, EDGE_X + xmax * 0.006], [tick_bot, tick_top],
                    color=OFFSCALE_CAP, linewidth=2, zorder=5)
            for idx, (lab, v) in enumerate(sorted(clipped, key=lambda t: t[1])):
                sc_color = cfg["scenario_colors"][lab]
                ax.text(EDGE_X + xmax * 0.01, tick_bot - 0.03 - idx * 0.15, f"{v:,.0f}*", ha="left", va="top",
                        fontsize=7.6, color=sc_color, fontfamily="Poppins SemiBold", zorder=LABEL_Z)

    ax.set_yticks(ys)
    ax.set_yticklabels([CENTER_LABELS[c] for c in order], fontsize=11, color=TEXT_PRIMARY)
    ax.set_xlim(0, xmax * 1.18)
    ax.set_ylim(-0.75, ys[-1] + 0.95)
    ax.get_xaxis().set_visible(False)

    for spine in ax.spines.values():
        spine.set_visible(False)
    ax.tick_params(left=False)

    fig.suptitle(cfg["title"], x=0.03, y=1 - TITLE_TOP_IN / fig_height, fontsize=17, color=TEXT_PRIMARY,
                 ha="left", fontfamily="Poppins SemiBold")
    # cfg["subtitle"] stays the full descriptive text (source of truth for
    # when SHOW_CAPACITY_TIER is re-enabled); strip the capacity mention
    # from what actually renders while the tier is hidden.
    subtitle = cfg["subtitle"] if SHOW_CAPACITY_TIER else cfg["subtitle"].replace(", full buildout capacity", "")
    fig.text(0.03, 1 - SUBTITLE_TOP_IN / fig_height, subtitle, fontsize=10.5, color=TEXT_MUTED, ha="left")

    tier_legend = [
        Patch(facecolor=TEXT_MUTED, label="2025 (current)"),
        Patch(facecolor="none", edgecolor=TEXT_MUTED, hatch="///", label="2055 (forecast)"),
    ]
    if SHOW_CAPACITY_TIER:
        tier_legend.append(Patch(facecolor=lighten(TEXT_MUTED, 0.7), label="Full REMM capacity"))
    scenario_legend = [
        Line2D([0], [0], color=color, marker="|", markersize=10, markeredgewidth=2.2, linestyle="-", linewidth=1.6, label=lab)
        for lab, color in cfg["scenario_colors"].items()
    ]
    # Two independently self-centered legend rows (not one grid -- forcing
    # jobs's 2 scenario items into a 3-wide grid to match the 3 tier items
    # packs them left instead of centering them). Anchor x is 0.5 (true
    # figure center), not the axes' own geometric center: the axes reserves
    # ~20% of extra width on its right for value labels beyond the bars
    # (xlim goes to xmax*1.2) with nothing mirrored on the left, so the bars
    # themselves visually center close to figure fraction 0.5.
    legend_kwargs = dict(loc="upper center", frameon=False, fontsize=9, handlelength=1.4,
                          columnspacing=1.3, bbox_transform=fig.transFigure)
    legend1 = fig.legend(handles=tier_legend, bbox_to_anchor=(0.5, 1 - LEGEND1_TOP_IN / fig_height), ncol=len(tier_legend),
                          labelcolor=TEXT_MUTED, **legend_kwargs)
    fig.add_artist(legend1)
    fig.legend(handles=scenario_legend, bbox_to_anchor=(0.5, 1 - LEGEND2_TOP_IN / fig_height),
               ncol=len(scenario_legend), **legend_kwargs)

    if any_clipped:
        fig.text(0.03, 0.02, "* beyond this chart's scale -- marked > on its row", fontsize=8, color=TEXT_MUTED,
                  ha="left", style="italic")
    fig.text(0.97, 0.02, "Source: REMM 2055 run (WFRC)", fontsize=8, color=TEXT_MUTED, ha="right", style="italic")

    top_fraction = 1 - HEADER_HEIGHT_IN / fig_height
    bottom_fraction = FOOTER_HEIGHT_IN / fig_height
    plt.subplots_adjust(top=top_fraction, bottom=bottom_fraction, left=LEFT, right=RIGHT)
    plt.savefig(output_dir / cfg["out"], facecolor=fig.get_facecolor())
    plt.show()
