Purpose

How much of the Wasatch Front’s population lives somewhere they can actually choose to bike or take transit instead of drive? Transportation Choices answers that with one number per place: the percent of people within 1/4 mile of a dedicated bike facility, or of a frequent bus route, transit stop, or station.

That number only means something next to a point of comparison, so we compute it for three scenarios. Each scenario is a combination of two independent inputs that do not have to match: a socioeconomic (SE) forecast year, and a GIS facility vintage year (what’s actually built on the ground, or assumed built, as of some year).

Scenario SE year GIS vintage Reads as
Existing 2027 2027 2027 today
No Build 2055 2055 2032 2055’s population, with no further facilities built
RTP (Build) 2055 2055 2055 2055’s population, with the RTP’s planned facilities built

Comparing No Build against RTP isolates the effect of building the plan – same future population, different infrastructure. Comparing Existing against either 2055 scenario shows how much of that effect is just growth.

ImportantThe 2032 GIS vintage is a placeholder, not real data

Neither mode has a real 2032 facility layer yet – bike is waiting on a layer from Sarah/Hugh (via Suzie), transit on a LIN Stops file from Suzie. Until those arrive, 2032 is deliberately defined as “unchanged from 2027” (see GIS_VINTAGES below), so No Build 2055 currently only isolates the effect of population growth, not a true no-further-investment scenario. Re-run this page once the real 2032 data lands.

GIS facility data is incremental by vintage year and mode: each vintage layers new facilities on top of the previous one rather than restating everything from scratch. That’s what makes the pipeline easy to extend – adding a scenario is one line in SCENARIOS, and adding a GIS vintage is one entry in GIS_VINTAGES.

This replaces the _archive/ v9 arcpy scripts (01-08), which bundled SE and facility data together per scenario (so SE year and GIS vintage couldn’t vary independently) and filtered transit stops with a hardcoded route list.

Setup

Two dictionaries carry all of the above as data rather than as logic: GIS_VINTAGES encodes what each vintage adds and which earlier vintage it builds on, and SCENARIOS just points at a (se_year, gis_year) pair for each named scenario. Nothing downstream needs to change to add a scenario or a vintage – only these two structures do.

Build Facility Geometry — Bike

Bike facilities are line geometry, buffered directly: utah_bikeways’s Facility1 field distinguishes facility type, and "Not Available" is the only value that means no bike facility, so everything else – on-street bike lanes and trails alike – is existing network. The 2055 vintage adds the RTP 2027 Preferred Scenario’s active-transportation line projects as-is – every row in at_line_projects is already a bike path facility type (shared-use path, trail, bike lane, sidepath, etc.), matching utah_bikeways’s own facility categories. The companion point layer (at_point_projects) is pedestrian/bike crossings, not bike-path segments, so it’s excluded here – WFRCAnalytics/GIS-RTP-Phasing-Criteria treats those crossings as a separate network-connectivity attribute rather than part of the facility network.

Each vintage’s cumulative network is its own adds plus everything the vintage it builds_on already had – so a vintage with nothing new yet (2032, for now) is simply identical to the vintage beneath it, not empty. Buffering and dissolving that cumulative network once per vintage gives the geometry every scenario needing that vintage can reuse.

Build Facility Geometry — Transit

Transit works differently in a way that matters for the buffer, not just the source: it’s built from stop/station points, never from route linework, and only from a subset of stops –

  1. LRT/CRT fixed-guideway stations, caught by mode containing TRAX or FrontRunner, and
  2. frequent bus stops only – uta_routes filtered to the frequent/fixed-guideway service tiers, matched back to stops through the comma-separated route field.

Every other bus stop is excluded. This two-part filter replaces v9’s hardcoded route list with something that updates itself as UTA’s service changes.

The 2055 vintage adds the RTP’s transit projects, but a planned rail or BRT corridor arrives as a line, not a point – so each line project is reduced to its centroid here, keeping the whole transit buffer point-based rather than letting new corridors buffer like a continuous bike facility would. Not every project qualifies, though: only LRT/CRT/streetcar rail and high-frequency bus (BRT, Enhanced Bus) project types count toward this mode, mirroring the Rail/BRT buffer-tier grouping WFRCAnalytics/GIS-RTP-Phasing-Criteria uses (which buffers FrontRunner, TRAX, and the Sugar House Streetcar together as one fixed-guideway-equivalent tier, separate from core local bus). Exploratory corridors, corridor preservation, transit/mobility hubs, maintenance facilities, park & rides, and gondolas are excluded – they aren’t LRT/CRT/high-frequency-bus stops themselves.

Prepare TAZ Geography

TAZ geometry itself doesn’t change across scenarios – only the population joined onto it does (that happens in Section 8, per scenario). So this runs once: filter to the four WFRC counties, and add the fields every downstream calculation needs – Region (a constant, for the region-level rollup), CountyName, and each TAZ’s total area in acres.

Compute Compatible-Area % by Scenario

We don’t know how population is distributed within a TAZ, only its total – so where a facility buffer only partly covers a TAZ, we assume population spreads evenly across the TAZ’s area and credit that TAZ with the same share of its population: HHPOPPiece = HHPOP * (piece area / total area). Summing HHPOPPiece over all pieces and dividing by total HHPOP for a geography gives the percent of its population within 1/4 mile of a facility – which is exactly SCENARIOS × modes × geography levels worth of one number each, so the result is a single tidy table rather than the nine separate CSVs the old per-scenario scripts produced.

Show the code 
GEOGRAPHY_LEVELS = ["Region", "CountyName"]  # add "SmallArea" once a workshop-area boundary exists

results = []
for scenario in SCENARIOS:
    se_path = PATHS["se_dir"] / f"SE_{scenario['se_year']}.csv"
    assert se_path.is_file(), f"Missing SE file: {se_path}"
    se = pd.read_csv(se_path)
    se.columns = se.columns.str.lstrip(";")  # v10 export has a stray leading ';' on the header row

    taz_se = taz.merge(
        se[[CONSTANTS["se_join_field"], "HHPOP"]], on=CONSTANTS["se_join_field"], how="left"
    )

    for mode, buffers in (("bike", bike_buffers), ("transit", transit_buffers)):
        pieces = gpd.overlay(taz_se, buffers[scenario["gis_year"]], how="intersection")
        pieces["AcresPiece"] = pieces.geometry.area / 4046.8564224
        pieces["HHPOPPiece"] = pieces["HHPOP"] * pieces["AcresPiece"] / pieces["AcresTotal"]

        for level in GEOGRAPHY_LEVELS:
            totals = taz_se.groupby(level)["HHPOP"].sum()
            piece_totals = (
                pieces.groupby(level)["HHPOPPiece"].sum().reindex(totals.index, fill_value=0)
            )
            pct = piece_totals / totals
            for geography_name, value in pct.items():
                results.append(
                    {
                        "scenario": scenario["name"],
                        "mode": mode,
                        "se_year": scenario["se_year"],
                        "gis_year": scenario["gis_year"],
                        "geography_level": level,
                        "geography_name": geography_name,
                        "pct_near_facility": value,
                    }
                )

tidy = pd.DataFrame(results)
print(f"Tidy results: {len(tidy)} rows")

Visualization

No Build 2055 and RTP 2055 are alternate futures, not consecutive years – both branch from the same Existing 2027 baseline, so each chart draws two separate lines per county forking from that shared starting point: dashed for No Build, solid for RTP. Pick one or more counties below; both charts update together, and the gray lines are always the WFRC region, so any county reads directly against the regional reference rather than in isolation. Hover any point for its exact value.

Show the code

// Reshape {scenario, pct_near_facility} rows into {entity, path, year, value}
// fork segments: one "No Build" segment and one "RTP" segment per entity,
// both anchored at the same 2027 value.
function branchRows(modeKey, geoLevel, namesFilter) {
  const rows = tc_data.filter(
    (d) => d.mode === modeKey && d.geography_level === geoLevel && (!namesFilter || namesFilter.includes(d.geography_name))
  )
  const existing = new Map(rows.filter((d) => d.scenario === "existing_2027").map((d) => [d.geography_name, d.pct_near_facility]))
  const out = []
  for (const [scenarioKey, path] of [["no_build_2055", "No Build"], ["rtp_2055", "RTP"]]) {
    for (const d of rows.filter((d) => d.scenario === scenarioKey)) {
      const start = existing.get(d.geography_name)
      if (start === undefined) continue
      out.push({entity: d.geography_name, path, year: 2027, value: start})
      out.push({entity: d.geography_name, path, year: 2055, value: d.pct_near_facility})
    }
  }
  return out
}

        fontSize: 12,

      }),
    ],
  })

NoteKnown rough edges

This is a first pass, not a final design: colors are tuned for light mode only (no separate dark-mode palette yet), the fork layout hardcodes existing_2027/no_build_2055/rtp_2055 as the three scenario names (adding a fourth scenario – e.g. a second “build” alternative – needs branchRows() updated, not just SCENARIOS), and the “pp vs No Build” annotation quietly disappears rather than erroring if either 2055 scenario is renamed or removed.
