Purpose

How much of the Wasatch Front’s population lives somewhere they can actually choose to bike or take transit instead of drive? Transportation Choices answers that with one number per place: the percent of people within 1/4 mile of a dedicated bike facility, or of a frequent bus route, transit stop, or station.

That number only means something next to a point of comparison, so we compute it for three scenarios. Each scenario is a combination of two independent inputs that do not have to match: a socioeconomic (SE) forecast year, and a GIS facility vintage year (what’s actually built on the ground, or assumed built, as of some year).

Scenario SE year GIS vintage Reads as
Existing 2027 2027 2027 today
No Build 2055 2055 2032 2055’s population, with no further facilities built
RTP (Build) 2055 2055 2055 2055’s population, with the RTP’s planned facilities built

Comparing No Build against RTP isolates the effect of building the plan – same future population, different infrastructure. Comparing Existing against either 2055 scenario shows how much of that effect is just growth.

ImportantThe 2032 GIS vintage is a placeholder, not real data

Neither mode has a real 2032 facility layer yet – bike is waiting on a layer from Sarah/Hugh (via Suzie), transit on a LIN Stops file from Suzie. Until those arrive, 2032 is deliberately defined as “unchanged from 2027” (see GIS_VINTAGES below), so No Build 2055 currently only isolates the effect of population growth, not a true no-further-investment scenario. Re-run this page once the real 2032 data lands.

GIS facility data is incremental by vintage year and mode: each vintage layers new facilities on top of the previous one rather than restating everything from scratch. That’s what makes the pipeline easy to extend – adding a scenario is one line in SCENARIOS, and adding a GIS vintage is one entry in GIS_VINTAGES.

This replaces the _archive/ v9 arcpy scripts (01-08), which bundled SE and facility data together per scenario (so SE year and GIS vintage couldn’t vary independently) and filtered transit stops with a hardcoded route list.

Setup

Two dictionaries carry all of the above as data rather than as logic: GIS_VINTAGES encodes what each vintage adds and which earlier vintage it builds on, and SCENARIOS just points at a (se_year, gis_year) pair for each named scenario. Nothing downstream needs to change to add a scenario or a vintage – only these two structures do.

NoteGeography levels beyond region and county

The v9 pipeline summarized results by workshop area as well as region and county. The wftcm_taz layer’s CITYGRP field reproduces that same workshop-area breakdown (its values – “Northern Salt Lake County,” “Southwest Salt Lake County,” “Southern Weber County,” etc. – line up with the v9 script’s SmallArea boundary names), so it’s used here as WorkshopArea. The layer’s WFTDM district fields (DISTLRG/DISTMED/DISTSML) add three more levels of their own – CityName, DistrictLarge, DistrictMedium, and DistrictSmall – all without needing a separate boundary source. (DISTSUPER/DSUP_NAME also exists on the layer, but within the WFRC footprint it’s identical to CountyName, so it isn’t added as its own level.)

Build Facility Geometry — Bike

Bike facilities are line geometry, buffered directly: utah_bikeways’s Facility1 field distinguishes facility type, encoded with AGRC’s 1/2/3 bikeway class suffixes (1 = physically separated cycle track, 2 = bike lane, 3 = shared roadway/shoulder). "Not Available" means no bike facility at all, but the class-3 family ("Other bike route, unspecified (3)", "Shoulder bikeway (3A)", "Marked shared roadway (3B)", "Signed shared roadway (3C)") is excluded too – it’s just a stripe or sign on a road shared with traffic, not a dedicated facility, and the v9 _archive/ script excluded the same codes (bike_l/bike_r NOT IN ('3','3A','3B','3C')). Everything else – bike lanes, buffered/protected cycle tracks, and trails – is existing network. The 2055 vintage adds the RTP 2027 Preferred Scenario’s active-transportation line projects as-is – every row in at_line_projects is already a bike path facility type (shared-use path, trail, bike lane, sidepath, etc.), matching utah_bikeways’s own facility categories. The companion point layer (at_point_projects) is pedestrian/bike crossings, not bike-path segments, so it’s excluded here – WFRCAnalytics/GIS-RTP-Phasing-Criteria treats those crossings as a separate network-connectivity attribute rather than part of the facility network.

Each vintage’s cumulative network is its own adds plus everything the vintage it builds_on already had – so a vintage with nothing new yet (2032, for now) is simply identical to the vintage beneath it, not empty. Buffering and dissolving that cumulative network once per vintage gives the geometry every scenario needing that vintage can reuse.

Show the code 
bike_cum = {}
for year in sorted(GIS_VINTAGES["bike"]):
    builds_on = GIS_VINTAGES["bike"][year]["builds_on"]

        pd.concat(parts, ignore_index=True), geometry="geometry", crs=CRS

Build Facility Geometry — Transit

Transit works differently in a way that matters for the buffer, not just the source. The 2027 base is built entirely from stop/station points, and only from a subset of stops –

  1. LRT/CRT fixed-guideway stations, caught by mode containing TRAX or FrontRunner, and
  2. frequent bus stops only – uta_routes filtered to the frequent/fixed-guideway service tiers, matched back to stops through the comma-separated route field.

(The 2055 vintage below does add route linework – planned corridors buffered as lines, same as bike – once it’s clear a single centroid point badly undercounts a corridor’s real coverage.)

Every other bus stop is excluded. This two-part filter replaces v9’s hardcoded route list with something that updates itself as UTA’s service changes.

Show the code 
_HF_ROUTETYPES_SQL = "'Frequent','BRT','Blue Line','Red Line','Green Line','S Line','FrontRunner'"
hf_route_abbrs = set(
    gpd.read_file(L["uta_routes"], where=f"routetype IN ({_HF_ROUTETYPES_SQL})")["lineabbr"].astype(
        str
    )
)

stops_raw = gpd.read_file(L["uta_stops"]).to_crs(CRS)
fixed_guideway = stops_raw[stops_raw["mode"].str.contains("TRAX|FrontRunner|BRT", na=False)]
hf_routes = stops_raw[
    stops_raw["route"].apply(
        lambda r: (
            False if pd.isna(r) else bool({t.strip() for t in str(r).split(",")} & hf_route_abbrs)
        )
    )
]
transit_2027 = gpd.GeoDataFrame(
    pd.concat(
        [fixed_guideway[["geometry"]], hf_routes[["geometry"]]], ignore_index=True
    ).drop_duplicates(),
    geometry="geometry",
    crs=CRS,
)
print(f"Fixed-guideway / BRT stops: {len(fixed_guideway)}")

The 2055 vintage adds the RTP’s transit projects. A planned rail or BRT corridor arrives as a line, not a point, but reducing it to a single centroid badly undercounts its real catchment – a corridor has stations spaced along its whole length, not clustered at its midpoint. Reasonableness-checking against the v9 benchmark confirmed this: collapsing lines to centroids put RTP 2050-equivalent transit coverage around 20%, far under the v9 pipeline’s reported 33% for 2050 RTP. So line projects are buffered directly as corridors here, the same way bike line facilities already are, while point projects (new stations) stay point-buffered.

NoteFull-line buffering is an interim choice, not the final answer

Buffering a corridor’s entire length overshoots too, in the other direction – it assumes a station is reachable from every point along the line, when real stations are discrete and spaced out (rail stops are often a mile or more apart), leaving real gaps that a full-line buffer doesn’t capture. Against the v9 benchmark this currently reads ~45% versus the reported 33% for 2050 RTP, roughly as far over as the centroid approach was under. The correct fix is what WFRCAnalytics/GIS-RTP-Phasing-Criteria already does: buffer each line, intersect with the real 2055 UF TDM model’s stop nodes to get actual station locations, then apply mode-specific buffer tiers (Rail 0.5 mi, BRT 0.35 mi, Core 0.25 mi). That needs the TDM network GDB, which isn’t available in this repo yet – full-line buffering is the deliberate placeholder until it is.

Not every project qualifies, though: only LRT/CRT/streetcar rail and high-frequency bus (BRT, Enhanced Bus) project types count toward this mode, mirroring the Rail/BRT buffer-tier grouping WFRCAnalytics/GIS-RTP-Phasing-Criteria uses (which buffers FrontRunner, TRAX, and the Sugar House Streetcar together as one fixed-guideway-equivalent tier, separate from core local bus). Exploratory corridors, corridor preservation, transit/mobility hubs, maintenance facilities, park & rides, and gondolas are excluded – they aren’t LRT/CRT/high-frequency-bus stops themselves.

Prepare TAZ Geography

TAZ geometry itself doesn’t change across scenarios – only the population joined onto it does (that happens in Section 8, per scenario). So this runs once: filter to the four WFRC counties, and add the fields every downstream calculation needs – Region (a constant, for the region-level rollup), the geography breakdowns (CountyName, WorkshopArea, CityName, and the WFTDM district hierarchy), and each TAZ’s total area in acres. These all come straight off fields already on the TAZ layer (CITYGRP, DISTLRG/DISTMED/DISTSML), so there’s no separate boundary source to fetch or maintain.

Show the code

Compute Compatible-Area % by Scenario

We don’t know how population is distributed within a TAZ, only its total – so where a facility buffer only partly covers a TAZ, we assume population spreads evenly across the TAZ’s area and credit that TAZ with the same share of its population: HHPOPPiece = HHPOP * (piece area / total area). Summing HHPOPPiece over all pieces and dividing by total HHPOP for a geography gives the percent of its population within 1/4 mile of a facility – which is exactly SCENARIOS × modes × geography levels worth of one number each, so the result is a single tidy table rather than the nine separate CSVs the old per-scenario scripts produced.

Show the code 
GEOGRAPHY_LEVELS = [
    "Region",
    "CountyName",
    "WorkshopArea",
    "CityName",
    "DistrictLarge",
    "DistrictMedium",
    "DistrictSmall",
]

results = []
for scenario in SCENARIOS:
    se_path = PATHS["se_dir"] / f"SE_{scenario['se_year']}.csv"
    assert se_path.is_file(), f"Missing SE file: {se_path}"
    se = pd.read_csv(se_path)
    se.columns = se.columns.str.lstrip(";")  # v10 export has a stray leading ';' on the header row

    taz_se = taz.merge(
        se[[CONSTANTS["se_join_field"], "HHPOP"]], on=CONSTANTS["se_join_field"], how="left"
    )

    for mode, buffers in (("bike", bike_buffers), ("transit", transit_buffers)):
        pieces = gpd.overlay(taz_se, buffers[scenario["gis_year"]], how="intersection")
        pieces["AcresPiece"] = pieces.geometry.area / 4046.8564224
        pieces["HHPOPPiece"] = pieces["HHPOP"] * pieces["AcresPiece"] / pieces["AcresTotal"]

        for level in GEOGRAPHY_LEVELS:
            totals = taz_se.groupby(level)["HHPOP"].sum()
            piece_totals = (
                pieces.groupby(level)["HHPOPPiece"].sum().reindex(totals.index, fill_value=0)
            )
            # Overlay geometry area can round-trip a hair above the true total
            # (e.g. 1.0000000000000004) due to floating-point noise in the
            # intersection -- clip rather than let it fail the sanity check below.
            pct = (piece_totals / totals).clip(upper=1.0)
            for geography_name, value in pct.items():
                results.append(
                    {
                        "scenario": scenario["name"],
                        "mode": mode,
                        "se_year": scenario["se_year"],
                        "gis_year": scenario["gis_year"],
                        "geography_level": level,
                        "geography_name": geography_name,
                        "pct_near_facility": value,
                    }
                )

tidy = pd.DataFrame(results)
print(f"Tidy results: {len(tidy)} rows")

# A handful of fine-grained geographies (e.g. Great Salt Lake open-water districts)
# have zero households, so their share-of-population is undefined (0/0 = NaN) --
# that's a legitimate result, not a bug, so it's excluded from the range check below.
n_undefined = tidy["pct_near_facility"].isna().sum()
if n_undefined:
    zero_pop_geos = sorted(
        tidy.loc[tidy["pct_near_facility"].isna(), "geography_name"].unique()
    )
    print(f"NOTE: {n_undefined} rows have undefined pct (zero-population geography): {zero_pop_geos}")

assert tidy["pct_near_facility"].dropna().between(0, 1).all(), (
    "Percentage outside [0, 1] -- check overlay/weighting"
)

Visualization

No Build 2055 and RTP 2055 are alternate futures, not consecutive years – both branch from the same Existing 2027 baseline, so each chart draws two separate lines per geography forking from that shared starting point: dashed for No Build, solid for RTP. Pick a geography level below (region, county, workshop area, city, or large/medium/small WFTDM district), then which geographies at that level to plot and which of the two 2055 scenarios to show – Bike and Transit live in separate tabs underneath, both driven by the same controls. The gray line is always the WFRC region, so any geography reads directly against the regional reference rather than in isolation. Hover any point for its exact value.

// Brand colors (_extensions/.../brand.yml) validated for CVD-safe separation
// (scripts/validate_palette.js from the dataviz skill) cover a handful of
// entities cleanly; d3's Tableau10 extends the palette for geography levels
// with more selections (e.g. large districts) without hand-picking more
// brand colors.
BRAND_PALETTE = ["#3762ad", "#c98b3a", "#a3423c", "#799f4c"]
function colorPalette(n) {
  const base = [...BRAND_PALETTE, ...d3.schemeTableau10]
  return Array.from({length: n}, (_, i) => base[i % base.length])
}

// Reshape {scenario, pct_near_facility} rows into {entity, path, year, value}
// fork segments: one "No Build" segment and one "RTP" segment per entity,
// both anchored at the same 2027 value.
function branchRows(modeKey, geoLevel, namesFilter) {
  const rows = tc_data.filter(
    (d) => d.mode === modeKey && d.geography_level === geoLevel && (!namesFilter || namesFilter.includes(d.geography_name))
  )
  const existing = new Map(rows.filter((d) => d.scenario === "existing_2027").map((d) => [d.geography_name, d.pct_near_facility]))
  const out = []
  for (const [scenarioKey, path] of [["no_build_2055", "No Build"], ["rtp_2055", "RTP"]]) {
    for (const d of rows.filter((d) => d.scenario === scenarioKey)) {
      const start = existing.get(d.geography_name)
      if (start === undefined) continue
      out.push({entity: d.geography_name, path, year: 2027, value: start})
      out.push({entity: d.geography_name, path, year: 2055, value: d.pct_near_facility})
    }
  }
  return out
}

function modeChart(modeKey, subtitle) {
  const isRegionLevel = selectedGeoLevel === "Region"
  const entityNames = isRegionLevel ? [] : selectedGeoNames
  const palette = colorPalette(entityNames.length)
  const entityColor = new Map(entityNames.map((name, i) => [name, palette[i]]))

  // The gray WFRC reference line is always drawn; when Region itself is the
  // selected level there's nothing else to plot, so entityRows is simply
  // empty and the chart reduces to that one reference line.
  const entityRows = branchRows(modeKey, selectedGeoLevel, entityNames).filter((d) => selectedPaths.includes(d.path))
  const regionRows = branchRows(modeKey, "Region", null).filter((d) => selectedPaths.includes(d.path))

  const regionAll = branchRows(modeKey, "Region", null)
  const regionNoBuild2055 = regionAll.find((d) => d.path === "No Build" && d.year === 2055)?.value
  const regionRtp2055 = regionAll.find((d) => d.path === "RTP" && d.year === 2055)?.value
  const showDelta = selectedPaths.includes("No Build") && selectedPaths.includes("RTP") && regionNoBuild2055 !== undefined && regionRtp2055 !== undefined
  const deltaPp = showDelta ? (regionRtp2055 - regionNoBuild2055) * 100 : null

  const pathCaptions = {
    "No Build": "Dashed = No Build 2055",
    "RTP": "Solid = RTP (Build) 2055",
  }
  const caption = `${selectedPaths.map((p) => pathCaptions[p]).join(" · ")} · both branch from the same 2027 baseline. Source: WFRC Transportation Choices (v10).`

  return Plot.plot({

          y: "value",

          strokeDasharray: PATH_STYLE[path].dash,
        }),
      ]),

        y: "value",

NoteKnown rough edges

This is a first pass, not a final design: colors are tuned for light mode only (no separate dark-mode palette yet), the fork layout hardcodes existing_2027/no_build_2055/rtp_2055 as the three scenario names (adding a fourth scenario – e.g. a second “build” alternative – needs branchRows() updated, not just SCENARIOS), the “pp vs No Build” annotation and entity end-labels quietly disappear rather than erroring if a scenario checkbox is unchecked, and unchecking both scenario checkboxes leaves a blank chart (axes only, every line and point – including the Existing 2027 baseline – disappears with it) rather than a message explaining why.

At a Glance

The region-level headline from the charts above, as a static summary – easier to screenshot, print, or drop into a slide than an interactive chart. Saved to output/region_pct.png, which the repo homepage also embeds directly, so it’s the same image in both places, not a separate one.
